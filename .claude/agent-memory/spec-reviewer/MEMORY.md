# spec-reviewer memory

- Requirements: when constitution P5 (authentication) applies and no sign-in feature exists, require a sign-in backlog item, or an explicit external dependency in the "Depends on" column. Saying "out of scope" is not enough.
- Requirements: the "Depends on" column must include every item needed to create the data a key scenario needs (for example, delete-at-quantity-0 needs the update-stock item).
- Requirements: rules stated only in process steps or exceptions (paging edge cases, re-checks, navigation memory) must also be numbered BRs.
- Requirements: glossary definitions and backlog text must not use the "Do not call it" synonyms of their own glossary.
- Requirements: the first backlog item must not include a view (product details, list) that a later item owns. Check for post-save or after-cancel overlap.
- Requirements: a capability inferred from a passing mention in the input (for example "status change" from "draft") must be labelled an assumption in In scope and in the backlog brief.
- Requirements: when document A must be built before document B, A's key scenarios must not rely on B's features. Check for build-order cycles across documents.
- Requirements: build-order statements must agree across Constraints, Risks and the Backlog note.
- Requirements: lockout rules must cover simultaneous attempts, attempts during a lockout, and duplicate submissions (including a double-submitted password change counting as a failed attempt).
- Requirements: when P5 applies, check the existing code (Program.cs) for every endpoint that answers without a session (health check, OpenAPI document), not only the one already known.
- Requirements: the transport-encryption rule must cover every request that carries a session, not only requests that carry a password.
- Requirements: when a rule from another requirements document is restated, point to it instead of copying it, so one rule is not owned by two documents.
- Specs: check FR wording against the glossary "Do not call it" list; template phrases like "Users MUST be able to" slip in.
- Specs: success criteria must not promise more than the FRs and approved BRs; edge cases must not fix an outcome that an open question in the same spec leaves open.
- Specs: an unconditional "MUST apply X" FR must not contradict later FRs that forbid X in some cases.
- Specs: one open decision shared by sibling specs is owned by one spec; the other points to it.
- Specs: "0 occurrences of X in logs" criteria need distinctive test values ("admin" matches ordinary log text); "without the value" in log rules should also say "or its length".
- Specs: secrets read from the environment can carry line breaks or control characters the UI field can never reproduce; runtime rules must use observable properties ("delivered with the system", not "committed").
- Specs: a storage rule (BR-008 / P4) needs an acceptance scenario that reads the stored result, not only an FR.
- Specs: scenarios that assert state across a restart depend on the spec that makes that state survive (sessions: 017 US4); name it and mark the scenarios.
- Specs (SPA): idle-timeout rules must say whether loading or reloading a page counts as activity; "show the sign-in page without a session" must be limited to opening a page so it does not contradict a sign-in prompt.
- Specs: when a surface "follows the same rules as" another, point to the whole sibling spec instead of listing a subset of BRs.
- Specs: a shared security counter fed from two entry points needs an FR and a test across both at the same time; security counters fail closed (an unrecorded failure must not let the attempt succeed).
- Specs: "processed once / repeat not counted" rules must say how a repeat is recognised (same session, same values, time window); a password change must handle the race with a sign-in using the old password.
- Specs: a sign-in spec separate from its brute-force protection must say it cannot be released alone (P5); statistical timing NFRs must stay measurable once a lockout stops attempts after 5.
- Specs: auth specs must cover a forged or altered session value and a sign-in from a browser that already has an Admin session.
- Plan hint: `Program.cs` uses `UseHttpsRedirection`, which redirects operations that R002 BR-034 says to refuse.
- R001 glossary "Do not call it" synonyms keep recurring in specs: "product data", "restock", "ordering", "amount", "reference", "remove". Check every section, including Assumptions and Out of scope.
- Spec: Given states and Independent tests must use only data the item's Depends-on chain can create (e.g. stock ≠ 1, Active, deleted); otherwise mark "seeded test data" or "once NNN exists".
- Spec: specs drafted in parallel must agree on shared decisions (history steps, extra request fields, trimming, discard prompt, invalid list parameters, P7 "no internal details" NFR, NFR numbering); one sibling must not silently answer what another asks.
- Spec: retry-after-network-error scenarios must cover a lost reply (operation saved, reply lost).
- Spec: "at most once"/"never again" rules in a delete spec must not forbid deleting again after a restore.
- Spec: every key scenario in the backlog brief (incl. "request without a signed-in session") must be a Given/When/Then scenario; a story delivering a P1 item's BR must not be P2.
- Spec: check-then-act guards (delete condition vs concurrent publish/adjust) must state check and effect are indivisible.
- Spec: an FR must not hold a MUST owned by a later backlog item; keep it in Out of scope / Edge cases.
- Spec: do not raise [NEEDS CLARIFICATION] on something an approved BR settles just because the item's Covers omits it; cite the BR and flag the Covers gap for /sdd-amend requirements.
- Spec: a duplicate-submit "at most once" rule for anything but adding a product is a new business rule (BR-028 covers add only) and conflicts with BR-035 "both count".
- Spec: a sub-view (dialog, inline form) must say whether it adds a browser-history entry, or QE-04 Back tests can't be written.
- Plans: a handler that runs field validation before a DB uniqueness check breaks "every invalid field at once" (FR-012); check the order, also against the replay/idempotency order.
- Plans: Minimal API body binding (JsonElement or typed) parses JSON before any custom reader; in Development ThrowOnBadRequest=true sends malformed JSON to UseExceptionHandler (500). Check claims of "malformed JSON → 400 with field messages".
- Plans: race tests on one shared in-memory SqliteConnection don't exercise unique-index races; require a named shared-cache in-memory DB plus direct repository tests (no Infrastructure.Tests project).
- Plans: 014 FR-018 owns the product management page and protected layout; R001 plans extend it, never create it or pick its route.
- Plans: existing HealthEndpointsTests uses a bare WebApplicationFactory<Program>; any new startup requirement (connection string, migration) must update it in the file structure.
- Plans: React Router navigation state lives in history.state and survives reload; "no state on reload → redirect" is wrong.
- Plans: SQLite returns DateTime with Kind=Unspecified; check UTC round trip in replies built from read-back data (replay paths).
- Plans: SqliteErrorCode 19 matches any constraint; unique violations are extended code 2067.
- Plans: when a SC limits the operator to "only N setup values", check every other setting the design requires (e.g. the connection string); P7 makes connection strings secrets, so there is no committed default.
- Plans: on SQLite the EF Core 9+ migration lock (`__EFMigrationsLock`) is not released when the process is killed; `MigrateAsync` at start needs a timeout and a refusal path, or later starts hang.
- Plans: EF Core `CommandError` / `SaveChangesFailed` log at Error level with parameter facets even when `Microsoft.EntityFrameworkCore` is set to Warning; expected-failure paths (PK race) need those categories lowered.
- Plans: data a spec calls "unusable/unreadable", and that a later spec hooks recovery into, must come back through the Result path, not the generic exception catch; EF owned types are optional (nullable columns) unless `Navigation().IsRequired()`.
- Plans: Application records that carry secrets need a redacting `ToString`/`PrintMembers` (or be a plain class).
- Plans: a SC requiring "0 occurrences in committed files" conflicts with literal secret values in test source; generate distinctive values at runtime.
- Plans: with `WebApplicationFactory`, an entry point that returns before `RunAsync` makes the factory's start succeed on a disposed host; test refused starts only as process tests.
