Ba làn đường, một đích đến

Yêu cầu lớn hoặc còn thô đi làn phân tích (BA) để tách thành backlog. Mỗi mục backlog trở thành một feature đi qua làn chính. Bug nhỏ đi làn nhanh. Cả ba gặp nhau ở build → verify → PR.

Làm một lần cho cả dự án, khoảng 10 phút.

nhánh: main
Cần có: git, node ≥ 20 và .NET SDK (bản LTS) trên PATH. Thiếu Node thì toàn bộ hook không chạy. Claude không tự cài các công cụ này. Ví dụ xuyên suốt trang này: một app quản lý nghỉ phép nội bộ tên LeaveManager.

Cách hoạt động
  • Claude hỏi từng câu một, tối đa 5 câu mỗi vòng, xếp theo mức ảnh hưởng: phạm vi > bảo mật/dữ liệu > trải nghiệm > chi tiết nhỏ.

3.3

Chia task

/sdd-tasks
Cấu trúc tasks.md
  • Setup → Foundation (chặn mọi phase sau) → một phase cho mỗi user story theo P1, P2, P3 → Polish.
  • Mỗi phase story là một lát cắt dọc: xong là chạy và test được riêng.
  • Trong mỗi phase, task viết test luôn đứng trước task cài đặt.
  • Mỗi phase kết thúc bằng một Checkpoint chứng minh phase đã xong.
  • Bảng Traceability cuối file: FR/NFR/kịch bản → task.
Định dạng task

- [ ] T005 [US1] Cài đặt use case gửi đơn — src/LeaveManager.Application/LeaveRequests/SubmitLeaveRequest/SubmitLeaveRequestHandler.cs
- [ ] T006 [P] [US1] Form gửi đơn — src/frontend/src/features/leave-requests/components/LeaveForm.tsx

/sdd-build              # phase đầu tiên chưa xong
/sdd-build phase 3      # một phase cụ thể
/sdd-build T007         # một task
/sdd-build all          # chạy hết, không dừng giữa các phase
Mỗi task
  1. Claude giao task cho software-engineer, kèm kịch bản chấp nhận và FR liên quan.
  2. Agent đọc architecture, spec, plan, contract; viết test (hoặc code tối thiểu) đúng tầng, đúng thư mục feature; chỉ dùng package trong danh sách cho phép.
  3. Claude tự kiểm bằng test-runner: test mới phải fail đúng lý do, code phải làm test pass. Không có file nào ngoài task bị đổi.
  4. Test vẫn fail thì gửi lại cho agent, tối đa 3 vòng; quá 3 vòng thì dừng và báo nguyên nhân nghi ngờ.
  5. Tick - [x], commit test(001): T004 … hoặc feat(001): T005 ….
Cuối mỗi phase (Checkpoint)
  1. Chạy toàn bộ test và lint.
  2. Thực hiện bước kiểm trong Checkpoint.
  3. code-reviewer soát diff của phase, kể cả lỗi kiến trúc (sai tầng, package lạ). software-engineer sửa các mục "Must fix", commit fix(001): review phase 3.
  4. Dừng lại báo cáo cho bạn.
Khi agent báo BLOCKED: đó là hành vi đúng. Tài liệu sai thì Claude đề xuất /sdd-amend …. Cần package chưa được phép hoặc chỗ đặt code mà kiến trúc chưa có thì đề xuất /sdd-architecture …. Sau đó Claude dừng lại chờ bạn quyết, không tự viết vòng qua. Xem mục Thay đổi & bug.
Mẹo
  • Build từng phase một và đọc báo cáo ở mỗi checkpoint. Phase story P1 xong là có MVP.
  • Hội thoại dài thì gõ /clear giữa các phase; /sdd-build đọc checkbox và chạy tiếp ngay.

Lặp đến khi hoàn chỉnh

Đi lần lượt qua các mục backlog theo thứ tự bảng ở bước 1.4. Mỗi lúc chỉ một feature dở dang.

feat/002 → feat/003 → feat/004
6.1

Chuyển sang feature kế tiếp

Lặp cho mỗi mục backlog 
git switch feat/002-approve-leave-request
git merge main        # đề xuất: kéo code của feature vừa merge vào nhánh này

Rồi quay lại chặng 2: /sdd-clarify → /sdd-approve spec → /sdd-plan → … → /sdd-pr.

Vì sao nên merge main? Các nhánh feature được tạo từ main cùng lúc ở bước 1.4, trước khi có code nào. BL-02 phụ thuộc BL-01, nên plan của BL-02 cần thấy code BL-01 đã merge. Đây là đề xuất của trang này, kit không tự làm bước đó.

6.2

Theo dõi tiến độ và độ phủ

Bất cứ lúc nào 
/sdd-status           # đang ở đâu, bước tiếp theo, tài liệu nào ⚠ stale
/sdd-analyze R001     # mọi BR đã có mục backlog? mọi spec còn khớp mục của nó?

Có thể hỏi tự nhiên: "còn lại gì?", "tài liệu có khớp nhau không?". Claude sẽ tự gọi hai lệnh chỉ-đọc này.

6.3

Nhìn lại quy trình

Mỗi 2–3 feature 
/sdd-retro 3

Gom lỗi lặp lại từ agent memory, verification.md, lịch sử revision và các commit fix(…). Lỗi gặp hai lần thành mục checklist cho reviewer; gặp ba lần thành hook hoặc lint rule. Ghi vào docs/retros/<ngày>.md, bạn chọn đề xuất nào được áp dụng.

Đích đến

App được coi là hoàn chỉnh khi

  • Mọi mục backlog của R001 có spec, và mọi spec đều đã merge vào main.
  • Mỗi feature có verification.md ghi READY TO MERGE và tasks.md ở trạng thái Done.
  • /sdd-analyze R001 kết luận "Consistent": mọi BG/BR được phủ, không spec nào lệch khỏi mục backlog của nó.
  • /sdd-status không còn feature dở dang hay tài liệu ⚠ stale.
  • ArchitectureTests xanh, và mọi package trong *.csproj và package.json đều có trong bảng "Allowed dependencies".
  • Đã chạy ít nhất một /sdd-retro và áp dụng các cải tiến cho các đợt tiếp theo.

Bug nhỏ: /sdd-fix

/sdd-fix Trang danh sách đơn bị crash khi nhân viên chưa có đơn nào. Log: TypeError at LeaveList.tsx:42

Chỉ dùng khi hệ thống sai so với hành vi mong đợi, sửa khoảng ≤ 3 file, không thêm thư viện, không đổi data model hay interface công khai. Ngược lại, dùng /sdd-spec hoặc /sdd-amend.

  1. Nhánh fix/NNN-slug, điều tra chỉ-đọc, viết fix.md: triệu chứng, cách tái hiện, hành vi mong đợi (Given/When/Then), nguyên nhân gốc file:line, phạm vi sửa.
  2. Bạn đọc rồi /sdd-approve fix.
  3. /sdd-build: test hồi quy viết trước và phải fail, rồi mới sửa.

Cần package hoặc quy ước mới: /sdd-architecture

/sdd-architecture add FluentValidation to Application for command validation

  2. Đưa bảng tác động và hỏi bạn xác nhận.
  3. Thêm dòng vào bảng, tăng Version (thêm package = minor, đổi luật tầng = major), commit docs: architecture v1.1.0 — ….
  4. Không cài gì ở bước này. Việc cài nằm trong một task của feature cần nó; plan cũ hơn version mới được liệt kê để cập nhật.

Cần làm ngoài quy trình

Ví dụ một spike thử nghiệm hoặc sửa gấp. Tạo .claude/settings.local.json (không commit):

{ "env": { "SDD_GATE": "off" } }

Khởi động lại Claude Code. Cổng code tắt; cổng duyệt, cổng kiến trúc và các guard vẫn bật. Nhớ xoá file khi xong. Hai công tắc khác cùng cách dùng, chỉ cho ngoại lệ có chủ đích: "SDD_DEPS": "off" và "SDD_EXTERNAL": "off".

Hook là lan can chống nhầm, không phải ranh giới bảo mật: code sinh ra bởi lệnh như npm init không đi qua hook. Quy tắc trong CLAUDE.md là lớp bảo vệ thứ hai.

Lan can: kiến trúc, dependency và thế giới bên ngoài

Chín thói quen để quy trình trơn tru

  1. Giữ spec nhỏ: 1–3 ngày mỗi feature; quá 5 user story thì tách.
  2. Đầu tư vào kịch bản chấp nhận: đó là thứ duy nhất được kiểm từ đầu tới cuối.
  3. Đọc thật trước khi /sdd-approve. Cổng duyệt chỉ có giá trị bằng việc đọc phía sau nó.
  4. Chạy /sdd-analyze trước /sdd-approve tasks.
  5. Mỗi lúc chỉ một feature dở dang.
  6. /clear giữa các phase và giữa các feature; mọi trạng thái nằm trong file.
  7. Không bao giờ tự tay sửa tài liệu đã duyệt; dùng /sdd-amend.
  8. Giữ danh sách dependency ngắn: mỗi lần /sdd-architecture add là một chi phí lâu dài.
  9. Retro đều đặn: lỗi gặp hai lần thành checklist, ba lần thành hook.
